# Lesson blocks for the apps: specification for review

**Version 1 draft, 8 November 2026. Status: approved in principle by the owner, with additions (included here);
not implemented.** Supersedes Part C of [SHARED-BACKEND-PLAN.md](SHARED-BACKEND-PLAN.md).

The content API publishes every written lesson as typed blocks, generated by `scripts/build-api.mjs` from the same
notes files the website draws. The apps never parse JavaScript, and a lesson written on the website reaches the apps
with no app update.

## 1. Files

| File | Holds |
|---|---|
| `kit/api/v1/catalogue.json` | Every course (exists) |
| `kit/api/v1/courses/<slug>.json` | A course's syllabus (exists). Adds `unitFile` and `blockTypes` |
| `kit/api/v1/courses/<slug>/units/<unit>.json` | **New.** One per written unit: `{ api: 1, course, unit, hash, lessons: [...] }` |

`hash` is the SHA-256 of the unit's notes file, so an app downloads a unit again only when it has changed.

## 2. A lesson

```json
{
  "id": "u03-05",
  "title": "Offer and acceptance",
  "module": "Formation",
  "level": "Introductory · Foundation",
  "lead": "What makes a valid offer, and when it's accepted.",
  "objectives": ["…"],
  "prerequisites": ["…"],
  "blocks": [ { "id": "u03-05.b7c41a2e", "type": "paragraph", "text": "…" } ],
  "questions": [ … ],
  "flashcards": [ … ],
  "terms": [ { "term": "…", "definition": "…" } ],
  "summary": ["…"],
  "references": [ … ],
  "reading": ["…"],
  "web": "/lawgradify/course/#u03-05"
}
```

`blocks` is the lesson in page order. `questions`, `flashcards` and `references` are also listed whole, because the
app uses them outside the lesson too (review, quizzes, a sources page). A `question` or `reference` block in
`blocks` points at one of them by id.

## 3. Every block

```json
{ "id": "u03-05.b7c41a2e", "type": "callout", "tone": "pitfall", "text": "…" }
```

- **`id` (always), stable.** If the notes line names one (`K#offer-def:`, as question tags already can), that's
  used. Otherwise it's the lesson id plus the first 8 hex characters of the SHA-256 of the block's type and
  normalised text, plus `-2`, `-3` for exact repeats. Moving a block keeps its id; editing its text gives a new one.
  Bookmarks and notes the learner attaches to a block should anchor to an explicit id where one matters.
- **`type` (always).** One of the types below.
- **Unknown types are skipped, never an error.** The course file lists every `blockTypes` its lessons use, so an
  app that meets one it can't draw can say "Update the app to see everything in this lesson", with a link to `web`.
- **Every block may have `web`**, a link to the same point on the website, used as the fallback for anything the
  app can't show natively yet.

### 3.1 Text

| `type` | Notes tag | Fields |
|---|---|---|
| `heading` | `H:` | `text` |
| `paragraph` | `P:` or an untagged line | `text` |
| `list` | consecutive `- ` lines | `items: [text]` |
| `callout` | `K:` `!:` `SAFE:` `EV:` | `tone`: `key`, `pitfall`, `safety` or `evidence`; `text`; `strength` (`established`, `contested`, `hypothetical`) for evidence |
| `equation` | `E:` | `tex`, `meaning?` |
| `example` | `X:` then `> ` lines | `text`, `steps: [text]` |
| `code` | **new** `CODE: language` then `> ` lines | `language`, `code` |
| `table` | **new** `TABLE: caption` then `> a \| b \| c` rows, first row the header | `caption`, `header: [text]`, `rows: [[text]]` |

### 3.2 Subject cards

| `type` | Notes tag | Fields |
|---|---|---|
| `case` | `CASE:` | `name`, `facts`, `held`, `principle` |
| `statute` | `LAW:` | `provision`, `provides` |
| `drug` | `DRUG:` | `name`, `mechanism`, `uses`, `adverse`, `monitoring` |

### 3.3 Media (new tags)

| `type` | Notes tag | Fields | Required for accessibility |
|---|---|---|---|
| `image` | `IMG: path \| alt text \| caption` | `src`, `alt`, `caption?`, `width?`, `height?` | `alt`. The build fails without it |
| `diagram` | `DIAGRAM: id` (defined in the course's `diagrams.js`) | `kind` (`flow`, `cycle`, `labelled`, `hierarchy`), `title`, `nodes: [{id, label, x?, y?}]`, `edges: [{from, to, label?}]`, `alt` | `alt`: a text description |
| `video` | `VIDEO: path \| title \| transcript path` | `src`, `poster?`, `title`, `captions` (WebVTT), `transcript`, `seconds` | Captions and transcript. The build fails without them |
| `audio` | `AUDIO: path \| title \| transcript path` | `src`, `title`, `transcript`, `seconds` | Transcript |

Media files live under the course (`kit/courses/<slug>/media/`) and are served from getgradify.com like everything
else. Generated explanations go through the same review as written notes before they're published.

### 3.4 Practice and activities

| `type` | Notes tag | Fields |
|---|---|---|
| `question` | `M:` `TF:` `MS:` `SEQ:` `MATCH:` `SA:` `NUM:` at that point in the lesson | `ref`: the question's id in `questions` |
| `activity` | `IX:` | `ref`: the interactive's id (from the course's `interactives.js`); `title`; `web` (always: activities open on the web until the app has a native version) |
| `reference` | `SRC:` at that point | `ref`: the reference's id in `references` |

## 4. Questions, flashcards, references

- **`questions`**: `{ id, kind, level, objectives, prompt, … }`. `kind` is one of `mcq` (`answer`, `distractors`, `why`),
  `truefalse`, `multi`, `order`, `match`, `short`, `numeric`. The fields for each come from the parser the website
  already uses (`kit/assess/model.js`), not a new one. `id` is the permanent question id where the notes give one
  (`law-u03-05-q2@1`), so an answer in the app is recorded in `assessment_attempts` against the same question as
  on the website.
- **`flashcards`**: `{ id, front, back, from? }`. `from` is `case`, `statute` or `drug` for cards made from those blocks.
  `id` is stable as for blocks.
- **`references`**: `{ id, citation, kind, date, link? }`. `kind` is `legislation`, `case`, `rule`, `guidance`,
  `standard`, `primary` or `secondary`.

## 5. Inline marks in `text`

The marks the notes already use, unchanged: `**bold**`, `*italic*`, `` `code` ``, `x^{2}`, `v_{0}`. The app renders
the same small set. Anything else is shown as plain text.

## 6. Compatibility rules

- Fields are only ever **added** within v1. A field's meaning never changes. A breaking change gets `/v2/` alongside
  `/v1/`.
- **New block types are not breaking:** old apps skip them, and `web` links to the website.
- An app must not fail on fields it doesn't know.

## 7. Checks (in CI, as for the rest of `kit/api/`)

- The unit files are regenerated and must match what's committed.
- Every lesson in every written unit is present, and every block has a known type.
- Block ids are unique within a lesson, question ids are unique within a course, and every `ref` resolves.
- Every `image` has `alt`, every `video` has captions and a transcript, every `audio` has a transcript, and every
  media file exists.
