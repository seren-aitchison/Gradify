# Gradify for iPhone, iPad and Mac: development brief

**Version 1, 8 November 2026.** The standing brief for any Claude session working on the native apps. Read it, and
[APP-API.md](APP-API.md), before changing anything.

## 1. What the apps are

One SwiftUI codebase, three destinations: iPhone (the main student app), iPad (a larger study workspace) and Mac (a
full study workspace). They are **clients of the same Gradify** as getgradify.com: the same courses, the same
Supabase accounts, the same progress. They are not a second product.

Rule: before building any app feature, check whether the website already has the data, API or logic for it
(`kit/api/`, `kit/data/`, `kit/learning/`, `supabase/`). If it does, reuse it. If the app needs something the
website doesn't expose, add it on the website side first (as an additive `/v1/` field), then use it in the app.

## 2. Where the code lives

A separate repository, **`gradify-apple`** (private), not a folder in this one. Reasons:

- The website and the app ship on different schedules: every push to `main` here runs test-and-deploy, and the
  subject builders push constantly. (The site is built from an allowlist in `scripts/build-site.mjs`, so an app
  folder wouldn't be published, but it would still have to be classified there and run through this CI.)
- The apps then depend only on the published API, which keeps that interface honest.
- Xcode project files and build products would churn this repository's history.

This repository stays the content engine. The app repository holds Swift code only and reads content over HTTPS.

## 3. How updates reach the apps

| Change | How the app gets it |
|---|---|
| A new course, school, lesson, question or flashcard | Automatically: the app reads `kit/api/v1/` and the notes files at launch and on refresh |
| Progress, study packs, reviews, AI answers | Automatically, through Supabase and the Edge Functions |
| A new kind of screen, navigation, or device feature | A new signed build, through TestFlight then the App Store |

To keep the third row small, the app renders lessons from data (blocks it knows: text, check question, flashcard,
worked example, source), and ignores block types it doesn't know rather than failing. A remote feature-flag
file (`kit/api/v1/app.json`, to be added) can switch supported features on and off without a release.

## 4. What already exists (8 November 2026)

- **Content API:** `kit/api/v1/catalogue.json` lists 10 courses (biology, chemistry, history, law, maths,
  nursing, pharmacy, physics, psychology, sociology). Each has `courses/<slug>.json`. Generated by
  `scripts/build-api.mjs`; CI checks it.
- **Lesson text** is in notes files that are JavaScript modules. They must be read as text, never run; see
  `kit/assess/canon.js`. Recommended first website-side task: have `build-api.mjs` also write each unit as
  JSON (`courses/<slug>/units/<unit>.json`), so Swift decodes with `Codable` instead of re-implementing the parser.
- **Catalogue registration is already automatic:** `build-api.mjs` includes every `kit/courses/<slug>/course.js`,
  and CI fails if `kit/api/v1/` is out of date. A Wave 1 or Wave 2 subject reaches the apps once its course folder
  is merged to `main`. A subject *site* with no course folder yet (EcoGradify today) isn't in the catalogue.
- **Supabase: not connected yet.** `gradify.config.js` has an empty URL and anon key, so on the website today
  progress is saved per browser only (see [BACKEND-STATUS.md](BACKEND-STATUS.md)). The app should do the same:
  work in "this device" mode, then sync once the project is verified. Don't claim cross-device sync in the app
  until `scripts/verify-backend.mjs` passes against the live project.
- **Tables the app will use:** `profiles`, `packs`, `cards`, `reviews`, `activity`, `plan_blocks`,
  `course_progress`, `assessment_attempts`, `tutor_usage`. Edge Functions: `study-pack`, `course-tutor`.
- **Mastery and evidence rules** are in `kit/learning/` (`evidence-class.js` and the Mastery Engine). Port the
  rules faithfully and test them against the same fixtures, so a lesson completed on iPhone counts the same as on
  the website.

## 5. Architecture

- SwiftUI, Swift 6, iOS/iPadOS 18+ and macOS 15+ (revisit when targeting newer only).
- Swift packages inside the app repo:
  - `GradifyCore`: models (`Course`, `Unit`, `Lesson`, `Card`, `Progress`), `Codable`, no UI.
  - `GradifyContent`: content API client and on-disk cache (works offline after first load).
  - `GradifyAccount`: Supabase auth (supabase-swift), session in the Keychain.
  - `GradifySync`: progress and reviews, local first (SwiftData), synced to Supabase when signed in.
  - `GradifyLearning`: spaced repetition and the mastery rules, ported from `kit/learning/`.
  - `GradifyDesign`: colours, type and components matching the kit's design system (`kit/styles/`), with each
    course's `accent` from the catalogue.
- One app target per platform family, sharing everything except layout: phone uses a tab bar, iPad and Mac a
  sidebar (`NavigationSplitView`).
- Keys: only the Supabase URL and **anon** key go in the app. Never a `service_role` or `sb_secret_` key.
  The Claude API is reached only through the Edge Functions, never directly from the app.

## 6. Build order

1. Project skeleton, packages, design tokens; the catalogue and a course syllabus loading from the live API.
2. Lesson reader with check questions, from the notes (or the JSON export once it exists).
3. On-device progress and flashcards with spaced repetition.
4. Sign-in and sync with Supabase (once the backend is verified).
5. Study packs from notes, and the AI tutor, through the Edge Functions.
6. Progress, Plan and Today screens; achievements.
7. iPad and Mac layouts polished; community and advanced features.

Each step ends with: it builds for iPhone, iPad and Mac; unit tests pass; it has been run in the Simulator and
screenshotted.

## 7. Tooling

- **Xcode 26.3 or later** on a Mac, with **Settings → Intelligence → Model Context Protocol → Allow external agents
  to use Xcode tools** switched on.
- Claude Code running **on that Mac** (not a cloud session: cloud sessions run on Linux and have no Xcode, Swift
  compiler or Simulator), connected with:

  ```bash
  claude mcp add --transport stdio xcode -- xcrun mcpbridge
  ```

- Cloud sessions can still do the website-side work (content API, JSON export, feature flags, Supabase) and review
  Swift code, but can't build or run it.

## 8. Release

- Needs an Apple Developer Program membership and an App Store Connect record (the owner's actions).
- TestFlight for every build that adds native features; App Store review for public releases.
- A student-facing app for under-18s needs the App Store's privacy labels, age rating and, for under-13s, the Kids
  category rules; check these before the first public release.
