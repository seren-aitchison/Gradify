## 3. Live Supabase `profiles` access rules

- **C (migrations):**
  - RLS is enabled on `public.profiles` (`20261028120000_gradify_core.sql:113`).
  - Policy `"own profile"`: `for all to authenticated using (id = auth.uid()) with check (id = auth.uid())` (line 122).
  - Insert, update and delete are revoked from `anon` (`20261113120000_client_privileges.sql:53`).
- **C (live, behaviour):** a read-only request as a signed-out visitor, using the site's public key, to
  `/rest/v1/profiles?select=id,learner` returned `[]` (HTTP 200). This is consistent with RLS hiding every row from
  `anon`. It is **not proof** the policy text matches, because an empty table would give the same answer.
- **O (live, definition):** needs a read-only query. No service-role key, no write access and no new credential are
  needed. The least-privilege options:
  1. **Preferred:** the owner runs this in the Supabase SQL editor (it only reads) and pastes the result:

     ```sql
     select c.relrowsecurity as rls_on, c.relforcerowsecurity as rls_forced
     from pg_class c join pg_namespace n on n.oid = c.relnamespace
     where n.nspname = 'public' and c.relname = 'profiles';
     select policyname, permissive, roles, cmd, qual, with_check
     from pg_policies where schemaname = 'public' and tablename = 'profiles';
     select grantee, privilege_type from information_schema.role_table_grants
     where table_schema = 'public' and table_name = 'profiles' and grantee in ('anon', 'authenticated');
     ```

  2. Reconnect the Supabase connector in **read-only** mode (it failed to connect this session), and I'll run the same
     queries.

**Goal:** the catalogue foundation, with no student data and no real ingestion. Repository only; no production change.
